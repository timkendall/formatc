# HIR API: the front-end's data model (src/sema/)

The contract for the engineers who port the parser (`vendor/bun/src/sema/parser/parser/*.rs`) and the handles
(`vendor/bun/src/lint/ast`). It describes what is in `src/sema/` and how every Rust construct maps to it, so that
`parser/expr.rs` etc. can be ported without reading the code of this directory. Sections 8 and 9 (the generated tables) are the
reference; sections 1-7 are the rules.

## 1. Conventions

* **One front-end per thread.** `hir` (`export const hir = new Hir()`), `nodeBases`, the lexer's `Names` are module-level singletons: module state is per
  worker thread under node and scriptc. They are allocated once, grow only, and are reset per file (`beginFile`). Nothing is freed.
  A parsed file is valid until the next `beginFile` on the same thread.
* **Ids** (`ExprId`, `StmtId`, ... all the `*Id` of `hir.rs`) are Int32 row indices into the table of that kind. **`NONE = -1`**
  (Rust `u32::MAX`; `Option<Id>` is `-1`). Test with `id < 0` or `id === NONE`.
* **Atoms** are Int32 ids of the file's atom table; `ATOM_NONE = -1` (Rust `Atom::NONE`). `A_foo` are the `known::foo` atoms (same numbers
  in every file). See section 5.
* **Positions** are byte offsets into the UTF-8 source (`hir.text`, a `Uint8Array`; `hir.sourceLen` bytes are valid: scratch buffers may be longer).
  Rust `u32::MAX` positions are `-1` (documented per column: `call.closePos`, `jsx.closePos`); `INCOMPLETE_TEMPLATE = -2` (`u32::MAX - 1`).
* **Lists.** A Rust `IdList<T>` and a Rust `Span<T>` are the SAME thing in TS: a `(start, len)` pair, where `start` indexes `hir.ids` (an Int32Array shared by all
  lists) and `ids[start .. start+len)` are the ids, in source order. There is no contiguity guarantee for the rows themselves (Rust's `Span` had one; no code may rely on
  it). A list field is two columns, named `<field>Start` / `<field>Len` (plain tables) or two payload slots (tagged tables, e.g. `a`+`b`).
  The empty list is any `(start, 0)`; use `(0, 0)`.
* **Enums without payload** (`Chain`, `UnOp`, `FnKind`, ...) are `export const CHAIN_NO = 0`-style integer constants (section 8), stored in `Uint8Array` columns.
  Bitflags (`Flags`) are Int32 bits `FLAG_*` with the bit numbers of Rust. `bool` is a 0/1 byte column (read `hir.col[i] !== 0`).
* **Enums with payload** (`ExprKind`, `StmtKind`, `TypeNodeKind`, `PatKind`) are a `tag` column (`EXPR_*`, `STMT_*`, `TYPE_*`, `PAT_*`: the order of the Rust `*Tag` enums) plus
  payload columns `a`, `b`, `c`, ... and a byte column `aux`. Section 9 says per variant which field is in which column, the generated builder `push<Table><Variant>(...)` and the
  generated accessors `<table><Variant><Field>(id)` (e.g. `exprDotObj(e)`, `exprDotName(e)`, `stmtIfTest(s)`).
  `Option<T>` fields hold `-1` for `None`. `Option<BinOp>` (`Assign.op`) is `0` = plain `=`, else `BIN_x + 1`.
* **Every read of a typed array that is stored/passed is `| 0`-ed**, every store too (cookbook rules 1-2). The generated accessors do it; direct column reads
  (`hir.fnKind[f] | 0`) must. Integer math is `((a | 0) + (b | 0)) | 0`.
* **TS narrowing gotcha.** `T_*`, `A_*`, `EXPR_*`... are declared `export const X: number = 5` (annotated on purpose: a literal type would make `if (lx.token === T_EQUALS) { lx.next();
  if (lx.token === T_OPEN_BRACE) ...` a type error "no overlap" because TS keeps the narrowing across the call). scriptc still folds them to constants.
* **No exceptions, no allocation per node.** Functions that return more than one value write the rest to a module-level slot (`getOut0()/getOut1()` in hir_util.ts,
  `getNdVector()/getNdId()` in node.ts, `names.key`, ...). A syntax error is a normal return: `lx.refusal !== 0`.

## 2. A file's life: the front-end API

```ts
import { hir } from "../hir.ts";            // tables
import { beginFile, finishHir } from "../hir_util.ts";
import { finishNodes } from "../node.ts";
import { Names } from "./names.ts";  import { Lexer } from "./lexer.ts";

// once per thread
const names = new Names();  const lx = new Lexer(names);

// per file (src: Uint8Array with >= len bytes; slack after len is fine and wanted)
beginFile(src, len);                          // hir.reset(), hir.text/sourceLen, reserveFor(len)
lx.begin(src, len);                           // names.begin (atoms of the previous file are forgotten), lexer state reset, hir.comments/commentDirectives cleared
lx.configure(dialect, isJsx, isJavascript, isJson, recovers);   // lib.ts: DIALECT_* bits (dialectBabel(isScript) for the formatter)
lx.next();                                    // first token
... parse: push rows into hir, take lists from stacks ...
processPragmasIntoFields(src, lx.leadingComments, recovers, names);   // pragmas.ts: hir.checkDirective, hir.references, jsx pragmas
finishHir();                                  // sorts parens, jsxExpressions, nonNullEnds, bodyStarts
finishNodes();                                // node.ts index space (only if node handles are used)
// lx.refusal !== 0  => the text was refused: why = lx.refusal (R_*), where = lx.refusedAt, lx.refusedAfter. hir.hasErrors etc. as in Rust.
```

`hir.comments` (rows of 2: start, end) is filled by the lexer: it is Rust's `File::comments`. `hir.commentDirectives` (rows of 3: start, end, CD_*) is `comment_directives`.
`lx.leadingComments` (rows of 2) are the comments before the first token (input of the pragmas).

## 3. Lazy bodies (`Lazy`, `LazyCells`): what they are and the TS equivalent

The doc comment of `hir.rs` says "the bodies of functions as lazy expressions"; **that is stale**: the parser does NOT defer function bodies. `Func.body` is
`FnBody::Block(IdList<StmtId>)` / `FnBody::Expr(ExprId)`, parsed eagerly in the one pass (`parser/func.rs`). In TS: `fnBodyKind` (`BODY_NONE/BLOCK/EXPR`),
`fnBodyA/fnBodyB` (block: statements list start/len; expression body: `fnBodyA` = the ExprId). The formatter forces nothing: it reads bodies from the tables.

What *is* lazy in Bun is data **derived from the HIR on first use**, behind `OnceLock` cells:
* `sema::hir::LazyCells`: `parents` (`node.Parent` of every tsgo node), `owners` (`FnId/ClassId` -> node), `ambient_or_type_places`, `type_query_places`,
  `class_extends_places`, `keyword_identifiers`. These serve the type checker (`bun check`). Not needed for formatting; not ported (node.ts documents the encoding only).
* `bun_lint::ast::Lazy` (`lint/ast/mod.rs`): `lines`, `tokens` (`TokenStore`), `parents`, `jsdoc`, `parenthesized` bitset, `sequence_roots`, `jsx_tags_with_dots`,
  `backslashes`, `unicode_escapes`, `directives`, `references`, ... computed the first time a rule/printer asks. The formatter asks for several (`parents()`, `lines`,
  `tokens`, `sequence_roots`, `parenthesized`).

TS design for the handles porter: **every lazily derived structure is a per-thread grow-only typed array plus a `built` flag that `beginFile` resets**; the accessor
builds on first use (`if (!built) build();`) and never otherwise. No `OnceLock`/atomics are needed (a file is formatted by one thread). Nothing is lazy in the parser:
always parse eagerly for formatting.

`class Lexer` (src/sema/parser/lexer.ts). One instance per thread, constructed with the thread's `Names`. Token state is in fields; the token kind is `lx.token` (`T_*`).
In the hot path read `lx.token`, `lx.start`, `lx.end`, `lx.atom`, `lx.newlineBefore` directly.

Token kinds: `T_*` in `parser/token.ts` (generated from the Rust enum order, which is load-bearing: `isReservedWord(t)` = `T_BREAK..T_WITH`, `isIdentifierOrKeyword(t)` = `t >= T_IDENTIFIER`,
`isAssignmentOperator` = `T_EQUALS..T_CARET_EQUALS`). `T::OpenBrace` is `T_OPEN_BRACE`, `T::KeyOf` is `T_KEY_OF`, the keyword `number` is `T_NUMBER_KEYWORD` (`T_NUMBER` is a numeric literal),
`T::EscapedReservedWord` is `T_ESCAPED_RESERVED_WORD`. Helpers: `isReservedWord`, `isIdentifierOrKeyword`, `endsExpression`, `canFollowMemberExpression`, `isAssignmentOperator`, `isModifier`,
`binaryPrecedence(t)` (or `PRECEDENCE[t]`), `tokenText(t)` (debug), `KEYWORDS`.

What the lexer yields per token kind: `T_IDENTIFIER` and every keyword/contextual keyword: `atom` = the name (decoded if it has an escape; then `hasEscape`), the token kind is the keyword's unless the word had an escape
(then `T_ESCAPED_RESERVED_WORD` / `T_IDENTIFIER`, or a refusal). `T_PRIVATE_IDENTIFIER`: `atom` includes the `#`. `T_STRING`: `atom` = the cooked value (WTF-8); `plainString === start` if
it has no escape. Templates (`T_NO_SUBSTITUTION_TEMPLATE/HEAD/MIDDLE/TAIL`): `atom` = cooked value (`\r\n` -> `\n`), `hasEscape` = an invalid escape (the parser decides: tagged templates allow it).
`T_NUMBER`: `number`. `T_BIG_INT`: `atom` = decimal digits. `T_JSX_TEXT`: `atom` = the text with JSX whitespace rules and entities applied. `T_REGEX` after `rescanSlash`: only boundaries (`start`, `end`).
Comments are trivia: recorded in `hir.comments` (and `leadingComments` while `fullStart === 0`), `newlineBefore` is set if a line break or a multi-line comment precedes the token.

## 5. Atoms

`names.ts` is the file's own atom table; `atom.ts` has the constants.
* `A_empty ... A_execScript` (`ATOM_FIXED` of them): Rust `atom::known::*` with the SAME numbers (Rust `known::foo` -> `A_foo`; `r#static` -> `A_static`, `let_` -> `A_let`). They are in every file.
  Keywords that are not known atoms are also pre-numbered (just after `ATOM_FIXED`); everything else is numbered by first occurrence in the file. Atom numbers carry no meaning (never order by atom).
* Interning: the lexer interns names, strings, bigints, templates, JSX text. For other text: `names.atomOfBytes(buf, start, end)` (copies if new), `names.atomOfSourceRange(start, end)` (the text is written in the source as it is),
  `names.atomOfString("lit")` (slow, tests), `names.findBytes(buf, start, end)` (no insert; -1 if absent). A decoded text is stored in `names.cooked` (`textBuf(atom)` says where).
* `names.atomToken(a)`: the keyword token of an atom (or `T_IDENTIFIER`): a function of the text.
* Comparing a name with a constant text in the parser: `lx.atom === A_foo` for known atoms; otherwise `names.atomIs(lx.atom, "text")`.
* `Atom::is_keyword_identifier` is `isKeywordIdentifier(a)`. `mention_bit`/`mentioned` (the linter's bloom filter) are not ported.
* Texts are bytes (UTF-8, WTF-8 for lone surrogates). `FileAtoms` = `names.textBuf/textStart/textLen`.

## 6. Hot-path rules the lexer follows (for the parser porters)

* `lx.src` reads inside loops are `this.src[i] | 0` directly (not hoisted into a local: a local array variable is a retain/release pair in scriptc and the loops have no stores, so LLVM hoists the loads itself).
* Cursor math `((p | 0) + 1) | 0`; tables are 256-entry `Uint8Array` (`FIRST`, `NAME_BYTE`, `STR_STOP`, ...); `FIRST[c] >= F_SIMPLE` means "this byte is a token by itself: `FIRST[c] - F_SIMPLE`".
* Do not pass numbers as `Uint8Array`/objects across hot calls; do not allocate in `next()` (it never does, except decoding a JS number from digits that need `parseFloat` and `BigInt` for non-decimal bigints).
* Measured (compiled, scriptc 0.3.0, this machine): see section 11.

## 7. Dialects and options (`lib.ts`)

`Dialect` (a struct of bools in Rust) is an Int32 of `DIALECT_*` bits: `typescript_5`, `ecmascript`, `babel`, `script`, `flow`, `oxc`, `oxc_names`. The formatter uses `dialectBabel(isScript)` for JS/TS,
`dialectFlow(isScript)` for `babel-flow`, `dialectFlowParser(isScript)` for `flow` (`lint/driver/fmt/mod.rs::language_and_dialect`). `Options` (class) has `isDeclarationFile`, `isJsx`, `isJavascript`, `isJson`, `awaitIsAName`,
`isModuleOrScript`, `recovers`, `readsJsdoc`, `dialect`. `optionsForPath(path, isScript, dialectFlags)` derives the file kind from the extension. The formatter parses in the non-recovering mode (`recovers = false`):
a text the parser cannot vouch for is refused and `bun fmt` reports an error for the file. The recovering mode (`recovers = true`) is kept in the lexer (error codes in `errors`/`flagged`) for the
parsers that need TypeScript's diagnostics; the lexer's `error()` records code+range only.

## 11. Measurements (tools/)

Corpus: `bench/vscode`, the 14,885 files of `.ts .tsx .js .mts .mjs .cjs` (197,961,549 bytes, 29,742,400 tokens, 233,265 comments), lexed to EOF, single thread, files already in memory (`tools/lex-vscode.ts`).

| | MB/s | notes |
| - | ---- | ----- |
| compiled (scriptc 0.3.0, `scriptc build tools/lex-vscode.ts`) | **345-357** (best of 5, load average 5-8 on the machine: runs vary by 3%) | 8.4-8.9 G instructions per pass (the counter itself varies by 4%) = ~295 per token = 44 per byte |
| node 24 (`node tools/lex-vscode.ts`) | 285-316 | |
| same, compiled, program also imports `Worker` (unused) | **241** | the "worker tax" of the cookbook is 30% here: every typed-array access is checked for a shared buffer and every loop back-edge counts. A formatter binary that spawns `Worker`s lexes/parses 30% slower than one that forks processes. Decide this at the architecture level. |
| compiled, identifiers not interned (upper bound for the scan itself) | 434 | atoms cost 20% |

What was tried and what it bought (instructions per pass of the corpus): FNV hash while scanning + byte comparison 9.2 G -> exact 12-byte keys (no byte comparison) 8.9 G -> one table lookup for class and simple-token (`FIRST[c] >= F_SIMPLE`) 8.64 G -> the key built during the name scan and the probe inlined 8.37 G. Before that: no local array variables in the hot methods (each is a retain/release pair), `((a | 0) + b) | 0` cursor math instead of `(a + b) | 0` (a double round trip per byte), `const` initialised by a literal (an expression like `x | 0` is a runtime load), a driver loop with locals instead of fields (-12%).
Not worth it (measured, reverted): DataView + 16-bit class table (SWAR) for the name scan (+4%), `Buffer.indexOf` for line comments (50 ns per call). The remaining cost is the dispatch on the first byte (a mispredicted branch per token on this
corpus), the byte loops of names and whitespace (~13 instructions per byte: bounds checks of `this.src[p]` and of the class table), and the probe (~100 instructions per atom). Rust's lexer scans with SIMD (`ScannerStops`); the 400 MB/s target was not reached.

Correctness (tools/):
* `node tools/lex-xcheck.ts --tsx`: every token boundary (start, end) of the 14,885 files against `ts.createScanner` (TypeScript 5.9.3, with the same decisions on regex / template continuation / JSX): **29,719,916 tokens, 0 mismatches**, and in every file all atoms have distinct texts (no duplicate atom for one text); 12 files the lexer refuses
  on purpose (11 contain a character like `…` that no TypeScript scanner accepts, 1 is a generic arrow in `.tsx` that the driver's heuristic reads as JSX); the atom of every ASCII name and plain string equals the source bytes and the token kind is a function of the text.
* `node tools/lex-unit.ts` (also compiled): 238 checks of decoded values (string escapes, templates, numbers, bigints, names with escapes, JSX text and entities), rescans, marks, comments and directives, operators.
* `node tools/lex-fuzz.ts` (also compiled): 20,000 mutated inputs x modes: no exception, always terminates, positions in range.
* `tools/hir-smoke.ts`: builders, accessors, sorting, growth (node and compiled).
Not tested: the recovering mode (`recovers = true`: error codes and recovery positions), `<!--` HTML comments, conflict markers, the oxc dialect; they are ports of the Rust code, branch for branch.
